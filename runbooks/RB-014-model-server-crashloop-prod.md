# Model server crashloop after config change

This runbook replaces RB-009, which was written when `inference-api` ran only
in staging. The symptom is identical in both environments. The remediation is
not, and applying the staging remediation in production causes an outage.

## Symptoms

- Inference pods in `ml-prod` restarting repeatedly, in CrashLoopBackOff
  following a deployment or config change
- The model server crashloops on boot; pods restart, fail, and restart again
- Container logs contain `FATAL: model config not found at ...`
- Restart count climbing on the inference pods; the rollout stalls partway with
  the previous ReplicaSet still serving
- The restarting pods never reach Ready

## Cause

The model server validates `MODEL_CONFIG_PATH` at boot and exits non-zero when
the file is absent, rather than starting with a partial configuration. This is
intentional: a model server that starts without its config would serve
predictions from an undefined revision.

In production, the config file is baked into the image at
`/etc/model/config.json`. A `MODEL_CONFIG_PATH` value pointing anywhere else is
almost always an env var that was changed by hand or carried over from a
staging manifest.

## Remediation

**Do not delete the model ConfigMap in production.** In `ml-prod` the ConfigMap
is the source of truth for the currently serving model revision and is not
regenerated by any pipeline. Deleting it takes down every replica, including
the healthy ones still serving traffic from the previous ReplicaSet, and the
revision it held cannot be recovered from the cluster.

The correct remediation is a rollback of the change that introduced the bad
path:

1. Confirm which revision introduced the change:

       kubectl -n ml-prod rollout history deployment/inference-api

2. Roll back to the previous revision. This restores the working
   `MODEL_CONFIG_PATH` without touching the ConfigMap:

       kubectl -n ml-prod rollout undo deployment/inference-api

3. Watch the rollout complete and confirm all replicas are Ready:

       kubectl -n ml-prod rollout status deployment/inference-api

4. Confirm the serving revision matches the intended model revision before
   declaring the incident resolved.

5. File a change ticket recording the bad value and the revision it came from.
   Production config changes are auditable and this one was not.

## Escalation

If the rollback does not restore Ready replicas within two rollout cycles,
escalate to the model platform on-call rather than retrying. A rollback that
does not converge means the previous revision is also broken, and the next
correct action is a pinned redeploy of a known-good image, not further
iteration in production.
