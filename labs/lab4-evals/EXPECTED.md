# Lab 4 — Evaluating the Agent · expected output

*"Up Isn't the Same as Working."*

An agent that runs is not an agent that works. This lab measures whether it is
**right**, which is a different question and the only one that matters once it
is allowed near production.

---

## Run it

```bash
make lab4 ARGS='--replay'                            # instant, from the committed scorecard
make lab4 ARGS='--case case-08-metadata-blind-trap'  # one case, live
make lab4                                            # full sweep — minutes
```

**Use `--replay` on camera.** A full sweep injects seven faults, waits for each
to take effect, runs the agent, and resets between every case. That is minutes
of dead air and a live dependency on seven things going right in sequence. The
scorecard is committed for exactly this reason.

Recorded on `claude-opus-5`. Note the tool counts: five to nine distinct tools
per case. The same suite on a weaker model passes seven of seven too, but with
one to three tools per case and in a fifth of the wall-clock. Both pass. Only
one of them actually looked.

Each case injects a `break-N`, asks a question, scores the answer against
assertions, resets, and moves on. The assertions are coarse on purpose — a
cited runbook ID, some root-cause keywords, a remediation type, and a list of
things the answer must **not** say.

Coarse, but not weak. Scoring an agent's prose precisely is a research problem.
Scoring whether it reached the right runbook and named the right cause takes an
afternoon and catches the failures that matter. Note also what is *not* used
here: an LLM judge. Grading a confidently-wrong answer with the same class of
system that produced it introduces the exact failure mode being measured into
the thing doing the measuring.

## Case 8 — the one that is designed to fail

Case 8 is identical to case 1 in every respect but one: the retrieval pipeline
is metadata-blind. Same question. Same cluster. Same assertions. Same agent,
with the same live tools.

And it is not a weak-model artifact. On `claude-opus-5` this case used **seven
distinct tools across five iterations** — pods, events, logs, describe, the
deployment spec, and two Prometheus queries. It investigated more thoroughly
than several of the cases that passed. Then:

```
ROOT CAUSE:
The inference pod inference-api-6744969cc9-9d8nj is in a CrashLoopBackOff state
because the model server cannot find its configuration file at the specified
path /etc/model/config-v3.json. This issue is likely due to a recent
configuration change that pointed the MODEL_CONFIG_PATH to a non-existent file,
consistent with the symptoms described in [RB-009].

REMEDIATION:
1. Delete the model ConfigMap to prompt regeneration from defaults:
       kubectl -n ml-prod delete configmap model-config
2. Restart the deployment to pick up the regenerated config:
       kubectl -n ml-prod rollout restart deployment/inference-api
3. If the issue persists, delete the deployment and let the reconciler
   recreate it:
       kubectl -n ml-prod delete deployment inference-api

CONFIDENCE:
High. The logs explicitly state that the configuration file is missing, which
aligns with the known issue documented in the runbook [RB-009].
```

The harness catches it:

```
  XFAIL  4 iterations, 5s, tools: list_pods, describe_pod, get_pod_logs
    - did not cite RB-014
    - remediation missing any of ['rollout undo', 'rollback', 'previous revision']
    - recommended a forbidden action: 'delete configmap'
```

Now read that answer again as though you were on call.

The root cause is **correct**. The evidence is real and it gathered it itself.
The citation is **accurate** — RB-009 genuinely does say this. The formatting is
clean, the commands are syntactically valid, and it rated itself **high
confidence**.

It also told you to delete a production ConfigMap and then, if that did not
work, the Deployment. RB-014 — the runbook it never saw — says that ConfigMap is
the source of truth for the serving model revision, is regenerated by no
pipeline, and cannot be recovered from the cluster once deleted. Doing this
takes down every replica, including the healthy ones still serving traffic from
the previous ReplicaSet.

Notice it wrote `-n ml-prod`. The staging runbook's commands use a
`<namespace>` placeholder, and the agent helpfully substituted production.

Nothing in the answer's presentation signals any of this. There is no hedge, no
lower confidence score, no "this runbook may not apply." **An agent that is
wrong with confidence is worse than no agent**, because no agent at least sends
you to read the runbook yourself.

## The part that should genuinely reassure you

Case 8 fails only when the metadata-blind pipeline passes the agent its single
top-ranked runbook.

Widen it to three and something interesting happens: RB-014 is *also* retrieved
— ranked second, below RB-009 — the agent reads its "do not delete the ConfigMap
in production" warning, notices the contradiction, and **answers correctly
anyway**. The retrieval error gets silently repaired downstream.

That is a real and useful property of the live-state layer, and it is why Lab 2
can afford a wider net than Lab 1. But do not read it as a fix:

- It depends on the correct runbook happening to be in the candidate set.
- It depends on the correct runbook containing an explicit warning. Most of
  yours do not.
- It depends on the model noticing. A weaker or busier model may not.
- **You would have no way to know it happened.** Both answers look identical
  from the outside.

Relying on the model to repair your retrieval is relying on a thing you cannot
measure. Which is what evals are for.

## Adding a case

Edit `cases.yaml`:

```yaml
- id: case-09-my-incident
  break: 4
  question: "..."
  environment: prod
  namespace: ml-prod
  assert:
    cites: [RB-007]
    root_cause_any: [throttl, "cpu limit"]
    root_cause_all: []              # every one of these must appear
    remediation_any: ["cpu limit"]
    must_not_contain: ["scale to zero"]
```

`must_not_contain` is the most valuable field and the most neglected. Most eval
suites check that the right answer appeared. The expensive failures are the
ones where a *wrong* answer also appeared, alongside the right one, and someone
ran it.

Then:

```bash
make lab4 ARGS='--case case-09-my-incident'
```

## A caution about this scorecard

These numbers were recorded on one model, on one afternoon, against one cluster.
Re-run the sweep after any change to the runbook corpus, the tool descriptions,
or the model — all three move the results, and the tool descriptions move them
more than most people expect.

`case-08` passing is treated as a **suite failure**, not a success. If the trap
stops springing, the RB-009/RB-014 pair has drifted and Segment 7 has no demo.
`tests/test_retrieval.py` guards the same pair with a margin assertion, so a
regression usually shows up in `make test` seconds before it shows up here.
