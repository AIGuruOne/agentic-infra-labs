# Lab 1 — The Knowledge Layer · expected output

You do not need a cluster or an API key to read this lab. Retrieval runs
offline against the 14 runbooks in `/runbooks`; only the grounded answer calls
a model.

Everything below is real output, captured on the reference Mac. Scores are
deterministic — BM25 over a fixed corpus — so yours will match exactly. The
wording of the grounded answers will differ slightly between runs and between
models; the *runbook each one follows* will not.

---

## The one thing this lab is about

Two commands. Same question, same corpus, same ranker. The only difference is
whether the pipeline uses the runbook frontmatter.

---

```
$ make lab1 ARGS='"why are prod inference pods repeatedly restarting?" --environment prod --namespace ml-prod'
```

```
  2. RB-006  score  3.39  environment=prod     PersistentVolumeClaim stuck Terminating          (not sent)

```

The corpus contains a staging runbook with the *same title* describing the
*same symptom*. It is not ranked lower here — it is not a candidate at all.
The filter is a hard pre-filter, not a boost.

The grounded answer that follows from RB-014:

> Confirm which revision introduced the change with `rollout history`, then
> `kubectl -n ml-prod rollout undo deployment/inference-api`, watch it with
> `rollout status`, and file a change ticket.
> **Do not delete the model ConfigMap in production.**

## 2. Without the metadata filter (the same pipeline, metadata-blind)

```
$ make lab1 ARGS='"why are prod inference pods repeatedly restarting?" --no-metadata-filter'
```

```

question why are prod inference pods repeatedly restarting?
corpus: 14 runbooks

ranked (metadata filter OFF)
  1. RB-009  score  4.84  environment=staging  Model server crashloop after config change       -> sent to model
  2. RB-014  score  4.08  environment=prod     Model server crashloop after config change       (not sent)
  3. RB-006  score  3.95  environment=prod     PersistentVolumeClaim stuck Terminating          (not sent)
  4. RB-003  score  3.13  environment=prod     Reconciling configuration drift between prod and staging (not sent)
  5. RB-013  score  2.90  environment=prod     Model server OOMKilled under batch load          (not sent)

```

RB-009 wins. It is lexically denser in the question's vocabulary and shorter,
and BM25 rewards both. Nothing has gone wrong with the retriever — it did
exactly its job. It has no way to know that this runbook does not apply to
production, because **the body never says so.** Only the frontmatter does, and
this pipeline threw the frontmatter away.

The grounded answer that follows from RB-009, verbatim from a real run:

> Recurrent restarts of the prod inference pods may be due to a model server
> crashloop caused by a misconfigured `MODEL_CONFIG_PATH`. To remediate this:
>
> 1. Delete the model ConfigMap so that it can be automatically regenerated
>    from defaults by the deployment pipeline:
>    `kubectl -n <namespace> delete configmap model-config`
> 2. Restart the deployment ...
> 3. If the issue persists, delete the deployment ...
>
> Make sure the pods reach the Ready state before considering the problem
> resolved [RB-009].

Read that against what RB-014 says about the same action:

> **Do not delete the model ConfigMap in production.** In `ml-prod` the
> ConfigMap is the source of truth for the currently serving model revision and
> is not regenerated by any pipeline. Deleting it takes down every replica,
> including the healthy ones still serving traffic from the previous
> ReplicaSet, and the revision it held cannot be recovered from the cluster.

The second answer is fluent, well-formatted, correctly cited, and would cause
an outage. Nothing about its presentation signals that it is wrong. An agent
that is wrong with confidence is worse than no agent.

## Why "ranked" and "sent to model" are different numbers

The pipeline ranks the corpus and passes only the top result to the model. That
split is printed so you can see it: the ranking shows what retrieval thought,
the `-> sent to model` marker shows what the answer was actually built from.

Pass more with `--top-k 3`. Try it on the unfiltered command — with RB-014 also
in context, a strong model notices the contradiction and recovers. That is
worth seeing too, because it shows how much of a retrieval bug a good model can
silently paper over, and why you cannot rely on that.

## Why this is the hybrid, and where dense retrieval would not help

Two retrievers with different blind spots: BM25 knows what a document is about
and nothing about where it applies; the metadata filter knows where it applies
and nothing about what it means.

Swapping BM25 for an embedding model changes which near-identical document wins
by a few points of cosine similarity. It does not change the fact that the
wrong environment's runbook is still in the candidate set. The filter is what
makes retrieval correct. The ranker only decides the order.

## Try this

- `--top-k 3 --no-metadata-filter` — watch a good model recover from the bad
  retrieval, and notice you had no way to know it needed to.
- `--environment staging --namespace ml-staging` — now RB-009 is the correct
  answer. It was never a bad runbook. It was a bad *match*.
- Ask a question the corpus does not cover and watch the model decline rather
  than improvise.
